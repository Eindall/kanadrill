# KanaDrill — contexte du projet

> Ce fichier est la référence à lire en premier pour reprendre le projet (humain, Cursor, Claude Code…).
> Il résume le besoin, les décisions prises (et celles écartées), l'état actuel et la suite.
> **Mets-le à jour** quand une décision change : il doit rester la source de vérité.

## 1. Le besoin

- Le propriétaire du projet apprend le japonais en cours (1 séance par semaine, organisme de formation). Son prof a fixé **un mois pour maîtriser les hiragana** : ensuite, les cours se feront sans romaji, uniquement en kana puis kanjis au fil de l'eau.
- Il a déjà des bases assez avancées et veut **réviser un peu chaque jour** : d'abord les kana (hiragana puis katakana), puis des **kanjis ajoutés au fur et à mesure** de ce qu'il apprend en cours.
- Application web **perso, dockerisée, auto-hébergée sur un VPS**, avec une base de données pour **enregistrer les résultats**.
- **Mobile friendly** (usage quotidien sur téléphone).
- **Multi-utilisateurs** : quelques amis qui parlent japonais pourront s'inscrire librement, chacun avec ses propres kanjis et sa propre progression.
- Les kanjis doivent pouvoir s'ajouter **automatiquement** (on saisit le caractère, les lectures et le sens se remplissent seuls).
- **Pas de limite quotidienne de nouvelles cartes** (décision du propriétaire). Le fonctionnement visé :
  1. un mode **« Apprendre »** : on lit la « page » (fiche détail : lectures, sens, ordre des traits…) de chaque kana et de chaque kanji ; les kanji s'**ajoutent à son dictionnaire perso**, les kana y sont **d'office** ;
  2. des **sessions** que l'on lance autant de fois qu'on veut, **paramétrées à chaque lancement** : nombre de cartes (15 / 30 / 50), types (hiragana, katakana, kanji : cases à cocher ; un type coché = **tous** ses éléments, on ne choisit pas kana par kana), exercices (QCM, texte libre, tracé : cases à cocher, tracé **réservé au mobile**) ;
  3. un **objectif quotidien** réglable dans le profil (« je veux tenter X cartes aujourd'hui »), affiché sur l'accueil avec une jauge de remplissage en %. Seul compte le nombre de cartes **tentées** : réussites et échecs sont indifférents.
  Sessions paramétrées et objectif quotidien sont **faits** (pour les kana) ; dictionnaire, « Apprendre » et kanji suivront (voir § 3 « Cible » et § 5).

## 2. Décisions prises

| Sujet | Décision | Pourquoi / alternatives écartées |
|---|---|---|
| Structure | Monorepo **Nx** : `apps/api`, `apps/web`, `libs/shared` | Types partagés front/back (DTO, règles de validation du pseudo). |
| Back | **NestJS 11** + **TypeORM 1.x** + **PostgreSQL 16** | TypeORM choisi (Prisma recommandé au départ, écarté) : le propriétaire veut se former dessus. Postgres plutôt que SQLite : multi-utilisateurs, écritures concurrentes. |
| Front | **Angular 22** (composants standalone, signals) + **Tailwind CSS 4** | Tailwind imposé par le propriétaire. |
| Mobile | **PWA** responsive, mobile d'abord : manifest + service worker Angular (`@angular/service-worker`) qui ne met en cache que la **coque** de l'application, jamais l'API ; pas de mode hors ligne | Une vraie app native est inutile ici. Pas de bouton « Installer » maison : on laisse le navigateur proposer l'installation (choix du propriétaire). |
| Authentification | **OAuth Discord et Google**, via **Passport** (`passport-oauth2`) ; Discord : scopes `identify email` (`prompt=none`), Google : `openid profile email` (`prompt=select_account` ; `prompt=none` échouerait sans session Google). `providerId` = ID Discord / `sub` Google | Écartés : pseudo + mot de passe (pas de SMTP pour réinitialiser), liens d'invitation. Discord seul au départ (pas d'e-mail stocké, filtre contre les bots, futur **bot Discord** qui retrouvera le compte via l'ID Discord) ; Google ajouté pour les amis sans Discord. **L'e-mail sert uniquement à détecter les doublons** (voir « E-mail haché et liaison de comptes »). |
| Inscription | **Libre** (premier login Discord ou Google = création du compte) | Choix du propriétaire. Limitation de débit côté API pour compenser. |
| Session | **JWT signé dans un cookie httpOnly**, dont le `jti` désigne une ligne de la table `auth_sessions` (une ligne = un appareil). **Expiration glissante : 48 h sans usage**, **plafond absolu de 30 jours** (reconnexion Discord), 20 sessions actives max par compte | Choix du propriétaire (expiration glissante courte). Le JWT seul ne suffisait pas : il ne se révoquait pas, et un compte supprimé gardait un cookie « valide ». La base fait foi : déconnexion réelle, liste des appareils, révocation. Pas d'empreinte du jeton à stocker : les `jti` seuls ne permettent pas de fabriquer un cookie (il faut la signature). Écartés : jeton opaque haché (JWT conservé par continuité), rotation de jetons de rafraîchissement (disproportionné ici). |
| Doublons et liaison de comptes | **Décision B : jamais de liaison automatique par e-mail.** Une connexion inconnue dont l'e-mail vérifié correspond à une identité d'un autre fournisseur ne crée **rien** et renvoie vers l'autre fournisseur ; la liaison se fait **depuis le profil**, connecté, en prouvant la possession des deux comptes | Écartés : liaison automatique par e-mail (prise de contrôle d'un compte si un fournisseur laisse passer une adresse non vérifiée ou mal gérée), e-mail en clair (donnée personnelle inutile à stocker), hash non salé (rejouable par dictionnaire : on utilise un **HMAC** à clé secrète). |
| Données de base | **Seed idempotent au démarrage de l'API** (upsert), pas une migration | Une migration ne se rejoue pas : corriger une lecture ou ajouter un jeu de caractères aurait imposé une nouvelle migration. Aucune commande manuelle. |
| Répétition espacée | **FSRS** (lib `ts-fsrs`) | Plus efficace que SM-2 (moins de révisions pour une même rétention), calibrable par utilisateur grâce aux `ReviewLog`. |
| Kanjis | Import **local** de KANJIDIC2 (lectures, sens fr/en) + **KanjiVG** (ordre des traits) + **listes JLPT N5-N1** de Jonathan Waller ; **tout** KANJIDIC2 (10 355 kanji avec un sens), classé par niveau, sens en français sinon anglais ; on demande le **sens et la lecture** | Pas de dépendance à une API externe susceptible de tomber. Licences CC BY-SA : prévoir une mention dans l'app. |
| Exercices | QCM + saisie du romaji dès la v1 ; **dessin du caractère sur mobile en v2** | Une vraie reconnaissance de caractère (deviner ce qui est dessiné) = gros chantier, écartée. Retenu : on **compare** le dessin au modèle KanjiVG connu (nombre, ordre, sens et forme des traits), l'app propose un verdict que l'utilisateur peut corriger (hybride) ; le modèle est celui de KanjiVG, sans graphies alternatives. |
| Nouvelles cartes | **Pas de limite quotidienne** ; c'est le **dictionnaire perso** qui joue ce rôle pour les kanji (une carte n'entre en révision que si l'utilisateur l'a ajoutée). **Les kana sont d'office dans le dictionnaire** : cocher « hiragana » = tous les hiragana, sinon aucun | Choix du propriétaire. Écarté : limite de N nouvelles cartes par jour (existait à l'étape 4, **retirée** par la migration `DailyGoal`). |
| Sessions | **Paramétrées à chaque lancement** (nombre de cartes, types, exercices), illimitées en nombre. Si la sélection ne contient pas assez de cartes, on **cycle** celles qui existent pour atteindre le nombre demandé | Chacun choisit son type d'exercice : si QCM et texte libre sont cochés, le mode est **tiré au hasard** à chaque carte (plus de règle liée à l'état de la carte). |
| Objectif quotidien | Réglage **par utilisateur** dans le profil (nombre de cartes à tenter par jour), jauge en % sur l'accueil. Compte les **réponses données** aujourd'hui, **réussies ou non** | C'est un objectif de motivation, **pas une limite** : on peut le dépasser et lancer d'autres sessions. Une session de 30 cartes valide un objectif de 30, quel que soit le résultat. |
| Séries et classement | Une **série** = jours consécutifs avec **au moins une réponse** (réussie ou non), jours calculés dans `APP_TIMEZONE` ; la série en cours survit jusqu'à minuit (elle compte jusqu'à hier). **Classement** : séries en cours, avec **option de masquage** par utilisateur (profil, activé par défaut) | Choix du propriétaire (« dès 1 réponse », timeline façon Duolingo). L'option de masquage est un ajout : l'inscription est libre, donc le classement expose pseudo, avatar et série à tout inscrit. Écartés : série conditionnée à l'objectif (trop punitive) ; bot Discord (plus tard). |
| Thème clair / sombre | Préférence **`system` (défaut) / `light` / `dark`** par appareil (`localStorage`), classe **`dark` sur `<html>`**, palette en **variables CSS** (`:root` / `.dark`) exposées à Tailwind par `@theme inline`. Anti-flash par **`public/theme-init.js`** (fichier externe, chargé de façon synchrone dans le `<head>`) | Palette sombre **dessinée**, pas inversée (contrastes ≥ 4,5:1 vérifiés). Écartés : script inline (la CSP nginx impose `script-src 'self'`), `dark:` dans chaque template (une cinquantaine de classes à doubler), préférence stockée côté serveur (inutile : réglage d'appareil). |
| Classements de la semaine | En plus du classement des séries : **« Réponses »** (nombre de cartes tentées depuis lundi) et **« Tracé »** (**points de tracé** = somme des précisions /100 des tracés comptés réussis, un tracé raté vaut 0). Remis à zéro **chaque lundi** (`APP_TIMEZONE`), mêmes règles de visibilité que les séries (option de masquage unique) | Choix du propriétaire (idée née de la note /100 du tracé). Écarté : classer par **précision moyenne** (deux tracés à 100 battraient 300 tracés à 92 : la somme récompense l'effort et la régularité). La précision est **recalculée par le serveur** d'après le dessin envoyé avec la réponse (non conservé) : on ne croit plus le client sur le score. |
| Déploiement | `docker compose` (db + api + web/nginx), à placer **derrière le reverse proxy du VPS** | Seul le conteneur `web` est exposé, sur 127.0.0.1. |

## 3. Architecture

```
apps/api            NestJS : auth Discord et Google (Passport), session JWT, profil, santé, migrations TypeORM
  src/app/auth        stratégies Discord / Google + garde OAuth, session (cookie JWT), guard JWT
  src/app/users       entités User / AuthIdentity, service, contrôleur /users/me
  src/app/database    DataSource (CLI TypeORM), liste des entités, liste des migrations
apps/web            Angular + Tailwind : pages login, accueil, profil, révision, « Apprendre » (kana, kanji), statistiques, classement, à propos ; proxy dev vers l'API
libs/shared         Types et constantes partagés (UserDto, règles du pseudo, fournisseurs OAuth), kana et conversion en romaji, correction des réponses, comparaison des tracés
```

- Le navigateur ne parle qu'à **une seule origine** : nginx (prod) ou le proxy du dev-server Angular (`/api` → `localhost:3000`). Pas de CORS, cookies simples.
- `User` (pseudo modifiable, avatar) ←1—n→ `AuthIdentity` (`provider`, `providerId` unique ensemble). Une identité = un compte chez un fournisseur ; plusieurs fournisseurs pourront être ajoutés plus tard sans toucher à `User`.
- Les migrations sont **appliquées au démarrage de l'API** (`migrationsRun: true`) ; `synchronize` est désactivé.

### E-mail haché et liaison de comptes (implémenté : `auth/email-hash.ts`, `oauth.guard.ts`, `oauth-state.service.ts`, `google.strategy.ts`, `users.service.ts`)

- **Empreinte** : `auth_identities.email_hash` (`varchar(64)` nullable, **index non unique**, migration `AuthEmailHash`) = **HMAC-SHA256** (clé `EMAIL_HASH_KEY`, ≥ 32 caractères, **distincte de `JWT_SECRET`**, vérifié au démarrage) de `email.trim().toLowerCase()`, en hex. Les points et les `+alias` ne sont **pas** normalisés. Calculée **seulement si le fournisseur atteste que l'e-mail est vérifié** (Google `email_verified === true`, Discord `verified === true`), sinon `null`. **Recalculée à chaque connexion** (et à la liaison) : elle repasse à `null` si l'e-mail n'est plus vérifié.
- **Donnée personnelle pseudonymisée** : l'e-mail en clair n'est **jamais** stocké, loggé ni renvoyé ; il vit le temps de `validate()` d'une stratégie (`ProviderProfile` ne porte que l'empreinte). L'empreinte n'est dans aucun DTO ni log, et est **supprimée en cascade** avec l'identité, donc avec le compte. Les logs d'échec OAuth ne contiennent que le statut HTTP / le code d'erreur, pas le corps de la réponse du fournisseur. Changer `EMAIL_HASH_KEY` invalide les empreintes existantes (elles se recalculent à la connexion suivante).
- **Connexion** (`UsersService.signIn`) : identité `(provider, providerId)` connue → connexion normale ; sinon, empreinte non nulle égale à celle d'une identité d'**un autre** fournisseur → **aucun compte, aucune session**, redirection `/login?error=account_exists&provider=<compte existant>&from=<fournisseur essayé>` (les deux paramètres sont validés contre `AUTH_PROVIDERS` côté front) ; sinon création du compte.
- **Liaison** (profil) : `POST /api/auth/:provider/link` (authentifié) pose un cookie de state **signé** `{ state, provider, mode: 'link', userId }` et renvoie l'URL d'autorisation ; au retour, le garde vérifie la signature, le state et le fournisseur, puis le contrôleur vérifie que la **session actuelle est celle de `userId`** (sinon `/profile?link_error=session`). Aucun rapprochement par e-mail. Refus si l'identité appartient à un autre compte (`link_error=conflict`) ou si le compte a déjà ce fournisseur (`provider_taken`). `DELETE /api/users/me/identities/:provider` dissocie, **409 pour la dernière identité** (condition vérifiée dans le `DELETE` lui-même).
- **Garde OAuth** : `OAuthGuard(provider)` généralise l'ancien `DiscordAuthGuard`. Le cookie `kd_oauth_state` est un JWT signé (`purpose: 'oauth-state'`, 10 min) : un jeton de session ne peut pas passer pour un state (pas de `purpose`, et le `jti` d'une session manque à l'inverse), et un state émis pour Discord est refusé sur le callback Google.
- **Limites connues** : (1) la détection ne couvre que les e-mails **vérifiés** et **identiques à la casse et aux espaces près** : `a.b@` et `ab@`, ou un `+alias`, ne sont pas rapprochés ; deux adresses différentes chez Discord et Google ne le sont pas non plus ; (2) un compte déjà existant n'a **pas d'empreinte** tant que son propriétaire ne s'est pas reconnecté (pour forcer : supprimer ses lignes de `auth_sessions` en base) ; un doublon créé avant cela n'est pas détecté ; (3) `account_exists` révèle qu'une adresse a déjà un compte, mais seulement à qui contrôle cette adresse chez le fournisseur : jugé acceptable (à revoir si besoin) ; (4) l'avatar reste celui du **premier fournisseur** du compte (il suit ses changements, pas ceux des fournisseurs liés ensuite) ; (5) un utilisateur ne peut lier **qu'un seul** compte par fournisseur ; (6) `prompt=none` sur Discord : au changement de scopes (ajout de `email`), l'écran de consentement s'affiche **une fois** pour les comptes existants (comportement documenté de Discord, à confirmer au premier essai en réel : si Discord renvoyait une erreur, retirer `prompt=none`) ; (7) Google : l'application doit être configurée dans la Google Cloud Console (écran de consentement + URI de redirection `${APP_URL}/api/auth/google/callback`), **pas encore essayé avec un vrai compte Google ni déployé**.

### Modèle d'apprentissage (implémenté, `apps/api/src/app/learning`)

- `Item` : un élément à apprendre (`type` : hiragana | katakana | kanji, caractère, `readings` = romaji acceptés dont le premier est la référence, `meanings`, `metadata` jsonb). Unique par (type, caractère).
- `UserItem` : l'état FSRS d'un item pour un utilisateur, colonne par colonne comme le `Card` de ts-fsrs (`toCard()` / `applyCard()` dans `fsrs-card.ts`). Unique par (utilisateur, item), index (utilisateur, échéance).
- `ReviewLog` : chaque réponse (note 1-4, durée en ms, date) + snapshot FSRS de la carte **avant** la réponse (requis par l'optimiseur de paramètres).
- Les valeurs de `Rating` / `State` sont recopiées dans `libs/shared` (`REVIEW_RATING`, `CARD_STATE`) ; un test vérifie qu'elles restent égales à celles de ts-fsrs.
- **Seed** : `SeedService` (`OnApplicationBootstrap`) fait un upsert idempotent des kana à chaque démarrage, après les migrations. Données dans `libs/shared/src/lib/kana.ts` (hiragana + lectures ; le katakana en est dérivé par décalage Unicode ; le fichier héberge aussi `kanaToRomaji`, que le front utilise pour corriger une saisie en kana). 104 kana par écriture : base 46 (ん et を inclus) + dakuten/handakuten 25 + yōon 33. Hors périmètre : kana rares (ゐ ゑ ヴ) et extensions katakana (ファ…). Corriger une lecture = modifier le fichier de données, pas de migration. Les **kanji** ont leur propre seed (voir « Kanji et dictionnaire perso »).

### Session de révision (implémentée, `learning/reviews.*`, `compose-session.ts`)

- **Réglage à chaque lancement** (`SessionConfig` dans `libs/shared`) : `count` (15 / 30 / 50), `types` (hiragana, katakana ; kanji viendra avec le dictionnaire), `modes` (`choice` = QCM, `typing` = texte libre, `drawing` = tracé, `reverse` = QCM inversé des kana, `meaning` / `reading` / `kanjiReverse` = exercices de kanji ; voir ci-dessous). Écran `/review/new` ; le dernier réglage est mémorisé par appareil (`localStorage`) ; la session se lance sur `/review?count=…&types=…&modes=…`.
- `GET /api/reviews/session?count=30&types=hiragana,katakana&modes=choice,typing` (validé strictement : taille parmi celles proposées, listes non vides, sans doublon, aucun autre paramètre). `composeSession` (fonction pure) compose `count` cartes parmi **tous** les items des types cochés, dans cet ordre : cartes **dues** (les plus en retard d'abord) → cartes **jamais vues**, **tirées au hasard** parmi toutes celles des types cochés (elles sont toutes au même niveau : pas d'ordre fixe, la sélection change d'une session à l'autre, hiragana et katakana se mélangent si les deux sont cochés) → cartes **vues mais pas encore dues** (la moins récemment vue d'abord) → si cela ne suffit pas, **cycle** : on repasse sur la même liste en tours successifs, sans jamais poser deux fois de suite la même carte (sauf s'il n'y en a qu'une). Le mode de chaque carte est tiré au hasard parmi les modes cochés. Le GET n'écrit rien : le `UserItem` est créé à la première réponse. Réponse : `counts` = `{ due, new, extra }` (`extra` = cartes déjà vues reposées pour compléter).
- QCM : 4 propositions, leurres = autres items du même type, jamais une réponse aussi valable comme « o » pour お/を.
- `GET /api/reviews/overview` : par type, cartes disponibles (`total`) et dues ; **réponses d'aujourd'hui** (`review_logs` depuis minuit, réussies ou non) ; objectif (`users.daily_goal`, défaut 30, 1–500, modifiable via `PATCH /users/me { dailyGoal }`, réglage dans le profil). Le « jour » suit `APP_TIMEZONE` (défaut `Europe/Paris`). Accueil : jauge `réponses du jour / objectif` en % (plafonnée à 100 à l'affichage, l'objectif n'est pas une limite) et bouton « Nouvelle session ».
- `POST /api/reviews { itemId, mode, answer, durationMs }` : le **serveur corrige** (`isRomajiCorrect`), déduit la note (`grading.ts`), puis, en une transaction, verrouille/crée le `UserItem`, écrit le `ReviewLog` (snapshot avant réponse) et applique FSRS (`enable_fuzz`). Notes : faux → Again ; juste → Good ; juste et > 8 s → Hard ; juste, **saisie** et < 2,5 s → Easy (jamais Easy au QCM). `durationMs` est plafonné à 120 s.
- Correction du romaji dans `libs/shared/src/lib/romaji.ts` (partagée API/front) : normalisation (casse, espaces, tirets, apostrophes) + variantes Hepburn / Nihon-shiki (shi/si, chi/ti, tsu/tu, fu/hu, ji/zi, sha/sya, cha/tya, ja/jya/zya, n/nn…). Les `readings` du seed contiennent déjà certaines variantes ; les règles complètent.
- Front (`features/review`) : une carte à la fois, grand caractère, retour immédiat calculé localement (le serveur fait foi ensuite), une carte **ratée est remise en fin de file** (`review-queue.ts` ; chaque place de la file a une `key`, car le cycle peut répéter un même item), bilan final (cartes, réussite sur première réponse, temps moyen, cartes à retravailler, prochaine échéance). Une sélection sans carte donne un 400 que la page affiche.
- **Limites connues** : `POST /reviews` n'est pas idempotent (un renvoi réseau compterait deux révisions) ; une bonne réponse à une carte en apprentissage n'est pas reposée dans la session (seules les ratées le sont) ; les réponses des cartes de complément (cycle, cartes pas encore dues) passent par FSRS comme les autres (choix assumé : un peu de précision de planification en moins) ; une première session peut proposer jusqu'à 50 cartes toutes nouvelles (on règle la taille soi-même).
- Le flux a été essayé à la main avec une vraie connexion Discord (OK) ; l'API est couverte par `reviews.integration.spec.ts`.

### Mode « Apprendre » pour les kana (implémenté, `learning/catalog.*`, `features/learn`)

- **Seed** : chaque kana a `metadata = { group, strokes }`. `group` ∈ `base` (46) / `voiced` (25, dakuten et handakuten) / `yoon` (33), dérivé des tables de `kana.data.ts` (`KANA_GROUP_ENTRIES`). `strokes` = traits dans l'ordre d'écriture (`StrokeDto` : chemin SVG `d` + position `n` du numéro, repère 109 × 109 de KanjiVG).
- **Tracés** : `tools/generate-kana-strokes.py` télécharge les SVG KanjiVG des kana simples (176 glyphes, hiragana et katakana) et écrit `seed/kana-glyphs.data.ts` (**généré et commité**, ne pas éditer ; relancer le script pour le régénérer). Les **yōon sont composés au seed** (`seed/kana-strokes.ts`) : le kana en i réduit à gauche + le petit ゃ / ゅ / ょ plus petit en bas à droite, les chemins SVG étant remis à l'échelle (`transformPath`, sans arcs : KanjiVG n'en utilise pas ici). Le seed met `metadata` à jour à chaque démarrage.
- **API** (`CatalogController`, protégé) : `GET /api/catalog` = les 208 kana dans l'ordre pédagogique, **sans** les tracés (lourds), avec `reading`, `group`, `mastery` ; `GET /api/catalog/:id` = fiche (lectures, tracés, `reps`, `lapses`, `nextDue`). 400 si l'id n'est pas un UUID, 404 si inconnu.
- **Maîtrise** (`mastery.ts`, déduite de l'état FSRS, 4 niveaux) : `unseen` (aucune réponse) → `learning` (Learning / Relearning) → `known` (Review) → `mastered` (Review et stabilité ≥ 21 jours, `MASTERED_STABILITY_DAYS`). Affichée sous chaque kana par trois segments (lisible sans la couleur, `aria-label` pour les lecteurs d'écran).
- **Front** : `/learn` (onglets Hiragana / Katakana, grilles par groupe ; le tableau de base reproduit la disposition classique : や ゆ よ en colonnes a u o, わ を aux extrémités, ん seul, `catalog-layout.ts`), `/learn/:id` (fiche + composant `StrokeOrder` : traits animés un par un par `stroke-dashoffset` avec `pathLength="1"`, fantôme gris, numéros, « Rejouer » ; `prefers-reduced-motion` : tout apparaît d'un coup), `/about` (licences KanjiVG et KANJIDIC2). Accès : lien « Apprendre » dans le menu du header (actif aussi sur les fiches), lien « À propos » en pied de page.
- **Pas fait** (volontairement) : le catalogue ne porte que les kana ; les kanji auront leur propre liste (recherche, filtre JLPT) au lot F, à cause de leur nombre. Pas d'étape « marquer comme lu » : consulter une fiche n'écrit rien.

### Exercice de tracé (implémenté, lot E : `drawing-pad.ts`, `review-page.ts`, `libs/shared/src/lib/drawing-score.ts`)

- **Déroulé** (mode `drawing`) : la carte affiche la **lecture** (« ka », jamais le caractère), l'utilisateur dessine le kana **au doigt** dans une zone de tracé, touche « Voir le modèle » ; le dessin et le **modèle animé** (ordre des traits, lot D) s'affichent côte à côte. L'app **compare** les deux et **propose un verdict**, qui **s'applique tout seul** : un bouton « Suivant » valide le verdict proposé, sans choix à faire (**mode hybride**). Pour le contester, deux boutons « Compte-le plutôt comme » proposent les deux autres verdicts (Raté / Presque / Réussi). Pas d'écran de résultat, on enchaîne.
- **Comparaison** (`scoreDrawing(user, model)`, fonction pure partagée, exécutée côté front) : le dessin est recadré sur le modèle (même centre, même plus grand côté : taille et position ne comptent pas) ; chaque trait est rééchantillonné (32 points) puis comparé au trait **de même rang** du modèle par l'**écart moyen** (en unités du repère 109 × 109, rapporté à la taille du trait, plancher 0,6). **Note /100** (`DrawingScore.score`) : un **nombre de traits** différent (exigé exact), un trait **hors d'ordre**, un trait **inversé** ou un dessin **trop petit** (< 25 % du modèle) valent **0** et un verdict « faux ». Sinon chaque trait vaut 100 points jusqu'à un écart de 6, 0 point à partir de 30 (linéaire entre les deux), et la note est la **moyenne** des traits : `good` ≥ 88, `fair` ≥ 60, sinon `wrong` (réglages dans `DRAWING_SCORE`). Un trait au-delà de `fairDistance` (15) est **signalé en rouge** (« s'éloigne du modèle ») et **empêche le « juste »**, mais ne condamne plus le tracé à lui seul (il pèse 1 / N). **Ordre et sens** : un trait n'est dit hors d'ordre / inversé que s'il ressemble **nettement mieux** (≤ 70 % de son écart à sa place, `confusionRatio`) à un autre trait ou à son propre modèle à l'envers ; un trait seulement brouillon n'est plus pris pour une faute d'ordre ou de sens. Le sens n'est pas jugé sous 14 unités de long (accents, petits traits). L'écran affiche « précision N/100 » (sauf 0).
- **Pourquoi ce changement** (retour du propriétaire : trop de « Faux » sur des traits éloignés alors que l'ordre était bon) : avant, **un seul** trait à plus de 15 unités suffisait à rendre le tracé faux, et la détection d'ordre / de sens se déclenchait sur tout trait brouillon qui ressemblait un peu à un autre. Sur des tracés simulés avec une déformation de 7 unités : « faux » 22,8 % → 3,8 % (kana) et 56,6 % → 7,1 % (kanji dense) ; « juste » à 5 unités : 72 % → 90 % (kana). Le prix : un **autre kana** de même nombre de traits passe en « Presque » dans ≈ 4 % des cas (contre < 1 %), jamais ou presque en « Juste » (< 1 %) ; pour un autre kanji, ≈ 1 %.
- **Limite connue** : le recadrage utilise la boîte englobante du dessin, donc **un trait très éloigné qui sort de la boîte** décale et redimensionne tous les autres traits (ils sortent alors tous de la zone de tolérance). Piste si les « Faux » persistent : ajuster l'échelle et la position par moindres carrés sur les traits qui collent le mieux, avant de comparer.
- **Modèle = KanjiVG tel quel** (choix du propriétaire) : on ne tolère pas les graphies alternatives (ex. さ en 2 traits au lieu de 3, c'est une erreur). Les yōon sont comparés sur leur composition (voir « Mode Apprendre »).
- **Calibrage** (testé sur les 208 kana avec des tracés simulés : échelle, décalage, déformation lisse et bruit ; `drawing-score.spec.ts`) : le modèle recopié ou redimensionné est toujours « juste » (100/100) ; une déformation légère n'est jamais fausse et reste « juste » plus de 9 fois sur 10 ; une déformation de 5 unités (≈ 5 % de la zone) est « fausse » dans 0,2 % des cas ; un trait inversé, deux traits permutés ou un nombre de traits différent sont toujours refusés ; un **autre** kana de même nombre de traits est refusé ≈ 96 % du temps (jamais « juste » ou presque). **Limites** : les paires qui se ressemblent (ね / ぬ, る / ろ / そ, れ / わ) passent parfois en « Presque » ; les seuils sont réglés sur des tracés **simulés**, à ajuster avec de vrais tracés au doigt si le verdict paraît trop sévère ou trop clément.
- **Réservé au mobile** : l'option n'est proposée que si le pointeur principal est tactile (`isTouchDevice()` : `(pointer: coarse)`, donc pas un portable à écran tactile). Un réglage mémorisé qui contient le tracé est nettoyé sur un appareil non tactile (`adaptToDevice`). L'API, elle, accepte `modes=drawing` quel que soit l'appareil : c'est une limite d'interface, pas de sécurité.
- **Zone de tracé** : un `<svg>` dans le repère 109 × 109 de KanjiVG (dessin et modèle superposables), événements pointeur (`touch-action: none`, événements coalescés), traits lissés en courbes quadratiques (`drawing-path.ts`), « Annuler le dernier trait » / « Effacer », 30 traits max.
- **API** : `SessionCardDto.strokes` (le modèle) n'est présent que sur les cartes `drawing`. Une carte sans traits retombe sur le QCM (`modesFor`). `POST /reviews` : au tracé, `answer` est le **verdict** (`DRAWING_ANSWERS` : `correct` / `fair` / `wrong`), que le **serveur croit sur parole** (il ne revérifie pas le dessin : le tracé n'est pas envoyé). `isAnswerCorrect` (partagée) : `correct` et `fair` comptent juste. Notes : faux → Again ; `correct` → Good ; `fair` → **Hard** ; jamais Easy ; Hard aussi au-delà de 30 s (`SLOW_DRAWING_MS`). La durée s'arrête à l'affichage du modèle.
- **À savoir** : la session envoie le caractère de chaque carte (`item.character`), y compris pour les cartes de tracé, où il est la réponse : l'interface ne l'affiche qu'après le dessin, mais il est visible dans le réseau. Sans importance ici. Idée si les seuils s'avèrent fiables : retirer la correction manuelle du verdict.

### Kanji et dictionnaire perso (implémenté, lot F : `kanji-seed.ts`, `kanji.*`, `dictionary.*`, `features/learn/kanji-browser.ts`)

**Décisions du propriétaire** : on demande **les deux** (sens et lecture) ; on importe **tout** KANJIDIC2, classé par **niveau JLPT** (N5 à N1 + « Autres ») ; sens **en français quand il existe, sinon en anglais** ; l'écran de lancement propose les exercices **kana, kanji, ou les deux**.

- **Données** (`tools/generate-kanji-data.py` → `apps/api/src/assets/kanji.json.gz`, **généré et commité**, 3,4 Mo) : KANJIDIC2 (lectures on/kun, sens fr/en, niveau scolaire, fréquence, nombre de traits), KanjiVG (tracés, avec la position des numéros, lus dans l'archive `main` : le XML unique n'a pas les numéros), niveaux JLPT. **10 355 kanji** (les 13 108 de KANJIDIC2 moins ceux sans aucun sens, surtout des kanji de noms rares) ; 6 388 ont un tracé ; 2 066 ont des sens français (le reste : anglais). Les mentions de radical (« radical (no. 72) ») sont retirées des sens.
- **Niveaux JLPT** : KANJIDIC2 n'a que **4 anciens niveaux** (N3 et N2 y sont confondus). Les niveaux N5 à N1 viennent des **listes de Jonathan Waller** (tanos.co.uk), via le dépôt `davidluzgouveia/kanji-data` (MIT) : 79 / 166 / 367 / 367 / 1 232 kanji ; ce sont des listes indicatives (le JLPT n'en publie plus d'officielles). Tout le reste (8 144) = « Autres ». Les licences sont sur la page « À propos ».
- **Seed** (`seed-items.ts`, `kanji-seed.ts`) : lu depuis `assets/kanji.json.gz` (webpack le copie à côté du bundle ; **le Dockerfile de l'API copie `assets/`**), inséré par lots de 250 en SQL brut avec `ON CONFLICT … WHERE … IS DISTINCT FROM` : rejoué à chaque démarrage, il **n'écrit que ce qui a changé** (≈ 2 s au démarrage). `items.readings` = tous les romaji acceptés (on et kun, avec et sans okurigana, et la voyelle longue abrégée : « jou » et « jo »), `meanings` = sens français sinon anglais, `sort_order` = 10 000 + rang (N5 d'abord, puis niveau scolaire, fréquence). `metadata` = `{ jlpt, grade, frequency, strokeCount, language, on, kun, strokes }`.
- **Dictionnaire perso** (`DictionaryService`) : `POST /api/dictionary { itemIds }` (≤ 500, ignore les kana et les doublons), `POST /api/dictionary/levels/:level` (tout un niveau), `DELETE /api/dictionary/:itemId` (supprime le `UserItem`, donc la progression ; l'historique `review_logs` reste). Ajouter crée un `UserItem` neuf. **Un kanji n'entre en révision que s'il y est** ; `POST /reviews` refuse un kanji hors dictionnaire.
- **Catalogue** : `GET /api/kanji/levels` (effectifs par niveau et dans le dictionnaire), `GET /api/kanji?level=&q=&offset=&limit=` (page de 100, recherche par **caractères**, par **sens** ou par **lecture en romaji**), fiche via `GET /api/catalog/:id` (champ `kanji` : on, kun, JLPT, grade, fréquence, nombre de traits, langue, `inDictionary`).
- **QCM inversé**, **un par famille, activables séparément** (choix du propriétaire) : `reverse` pour les kana, `kanjiReverse` pour les kanji (tous appareils). On voit la **lecture** d'un kana (« pu ») ou le **sens** d'un kanji (« sol, terre, terrain ») et on retrouve le **bon caractère parmi quatre** ; la réponse envoyée est le caractère choisi (`isAnswerCorrect` : égalité exacte avec `item.character`, un katakana n'est pas le hiragana de même lecture). Leurres (`buildReverseChoices`) : pour un kana, d'autres kana **du même type**, jamais un qui **se lise comme la lecture affichée** (お et を se lisent « o ») ; pour un kanji, d'autres kanji **du même niveau JLPT** (tirage de 60 par niveau : sinon la rareté du caractère trahit la réponse), jamais un qui **partage un sens** avec lui (comparaison sans la casse) ; si le niveau n'a pas assez de kanji, on complète avec les autres niveaux. Notation : jamais Easy ; Hard au-delà de 8 s (kana) ou 12 s (kanji). Retour : le caractère et sa lecture (ou, pour un kanji, son récapitulatif sens et lectures). Un exercice d'une famille ne s'applique pas à l'autre (`modesFor`, et `POST /reviews` refuse un exercice qui ne convient pas à l'élément).
- **Exercices par famille** : kana = `choice` (QCM de lecture), `typing` (saisie), `drawing`, `reverse` ; kanji = `meaning` (QCM du **sens**, leurres = sens d'autres kanji **dans la même langue**, jamais un sens valable du kanji), `reading` (saisie de la lecture en **romaji, hiragana ou katakana**, n'importe laquelle des lectures on ou kun), `drawing` (le kanji se dessine d'après son sens, avec ses lectures en aide), `kanjiReverse`. **Un seul état FSRS par kanji** : l'exercice est tiré au hasard à chaque carte parmi ceux cochés qui lui conviennent (`modesFor` : chaque famille a les siens, chaque exercice exige sa donnée ; sinon repli sur le QCM de kana / le sens). Correction partagée API / front (`libs/shared/src/lib/answer.ts`, `kana.ts` pour la conversion kana → romaji). Notation (`grading.ts`) : seuils plus larges pour un kanji (sens 12 s, lecture 4 s → Easy / 15 s → Hard).
- **Écran de lancement** : « Que réviser ? » (hiragana, katakana, kanji ; le kanji est grisé tant que le dictionnaire est vide, avec un lien vers « Apprendre ») puis « Exercices » par famille (**Kana** : QCM de lecture, saisie, QCM inversé ; **Kanji** : sens, lecture, QCM inversé) et « Écriture » (tracé, écran tactile seulement), seul exercice commun aux deux familles cochées. Cocher / décocher une famille ajuste les exercices (`reconcileModes`) ; une famille cochée sans exercice bloque le lancement.
- **« Apprendre »** : onglets Hiragana / Katakana / Kanji (état dans l'URL : `?tab=kanji&level=N5&q=…`, pour retrouver sa place en revenant d'une fiche) ; liste des kanji par niveau avec recherche et « Afficher plus », indicateur de maîtrise sous les kanji du dictionnaire (pointillé sinon), « Tout ajouter à mon dictionnaire » par niveau (avec confirmation) ; fiche : sens, lectures on / kun, ordre des traits animé (cadence resserrée au-delà de 9 traits), ajout / retrait du dictionnaire (retrait confirmé : la progression est effacée).
- **Tracé des kanji** : `scoreDrawing` marche tel quel (vérifié sur les 612 kanji N5 à N3 : copie fidèle toujours « juste », trait inversé / traits permutés / trait manquant toujours refusés, un autre kanji accepté 2 fois sur 2 436 : 八 / 入, 牛 / 午). Pour tenir compte des nombreux traits, la note est une **moyenne** : un trait éloigné ne pèse que 1 / N (voir « Comparaison » ci-dessus) ; il est signalé et empêche le « juste ».
- `items.sort_order` n'intervient **plus** dans la composition des sessions (les cartes jamais vues sont tirées au hasard) ; il sert à ordonner les listes du mode « Apprendre ».
- **Limites** : un kanji sans lecture (≈ 2 %) n'a pas d'exercice de lecture ; sans tracé KanjiVG (3 967 kanji, rares pour la plupart) pas d'exercice de tracé ni d'ordre des traits ; le QCM de sens prend ses leurres au hasard parmi tous les kanji (pas de proximité de niveau) ; un sens français de KANJIDIC2 est parfois très rare (« saumure ») quand il est choisi comme leurre ; le QCM n'accepte qu'un des sens proposés (le premier), la saisie de lecture accepte toutes les lectures.

### Thème clair / sombre (implémenté, `styles.css`, `core/theme*.ts`, `layout/theme-toggle.ts`, `public/theme-init.js`)

- **Jetons** : les couleurs de `styles.css` sont des variables (`--paper`, `--ink`…) définies sur `:root` (clair) et `.dark` (sombre), reprises par `@theme inline` : `bg-paper`, `text-ink`, `border-line`… s'adaptent sans toucher aux templates. `@custom-variant dark` existe mais n'est pas utilisé. `color-scheme` suit le thème (barres de défilement, champs natifs).

Rampe de maîtrise en variables (`--mastery-*`), inversée en sombre (le plus solide = le plus clair). Les marques de graphique restent à ≥ 3:1 en sombre ; en **clair**, `ink-faint` (2,8:1) et `mastery-learning` (2,5:1) sont sous 3:1 : valeurs d'origine du lot G, **inchangées** (voir « Limites »).

Il **duplique** clé et couleurs de `core/theme.ts` (un test de `pwa.spec.ts` les garde alignées). **nginx ne doit pas le mettre en cache** (nom sans hash : sinon une modification n'arriverait jamais) : il est dans la règle « jamais en cache » avec `ngsw-worker.js` (testé).

- **API** : `GET /api/leaderboard/weekly?metric=answers|drawing` (`WeeklyLeaderboardDto` : lundi de la semaine et du lundi suivant, entrées, `me`, `total`) ; `GET /api/leaderboard` (séries) est inchangé. Page `/leaderboard` : 3 onglets **Séries / Réponses / Tracé**, l'onglet est dans l'URL (`?tab=answers|drawing`) ; la page est chargée **à la demande** (`loadComponent`, pour tenir le budget du bundle initial).
- **Réponses** : toutes les réponses de la semaine (réussies ou non) ; détail = taux de réussite (note ≥ Hard). **Tracé** : `value` = somme de `review_logs.drawing_precision` des tracés de note ≥ Hard (un tracé corrigé « raté » vaut 0), détail = nombre de tracés faits.
- **Précision, recalculée côté serveur** : l'appareil envoie le **dessin** (`SubmitReviewRequest.strokes`, tracé seulement : points `[x, y]` dans le repère 109 × 109, allégés par `thinStrokes` : un point tous les ≥ 1 unité, arrondis au dixième, ≈ 1 Ko par tracé) ; `ReviewsService.submit` rappelle `scoreDrawing` (la même fonction partagée que sur l'appareil, contre le modèle KanjiVG de l'élément) et stocke le résultat dans `review_logs.drawing_precision` (migration `ReviewDrawingPrecision`, nullable + `CHECK` 0-100). **Le dessin n'est pas conservé.** Le client ne peut plus annoncer de score (un champ `precision` est refusé en 400). Validation : 1 à 40 traits, 1 à 400 points par trait, 4 000 au plus en tout, coordonnées finies ; 400 hors tracé ou si l'élément n'a pas de modèle. Sans dessin (anciennes réponses, ancien client en cache), la réponse compte mais **ne rapporte pas de points** : le classement « Tracé » démarre vide. L'appareil compare et envoie le **même** dessin allégé, donc la note affichée et celle du serveur sont identiques.
- **Règles** : semaine du lundi 00:00 au lundi suivant (heure de `APP_TIMEZONE`) ; seuls les utilisateurs **visibles** (`leaderboard_visible`) avec **plus de 0** sont classés ; rang partagé à égalité (1, 1, 3) ; 50 au plus ; chacun voit sa ligne (et son rang) même hors liste ; un utilisateur masqué ne fuit nulle part.
- **Tests** : `stats.integration.spec.ts` (frontières de semaine à minuit heure de Paris, égalités, masquage, tracés sans précision / ratés, validation du paramètre), `reviews.integration.spec.ts` (précision recalculée d'après le dessin, dessin d'un autre kana, champ `precision` refusé, dessins mal formés), `drawing-path.spec.ts` (`thinStrokes`), `weekly-board.spec.ts`. Vérifié dans Chrome (mobile, clair et sombre, API simulée). **Pas encore déployé** : la migration s'applique au démarrage de l'API.
- **Limites** : plus de fausse précision possible, mais **le modèle est envoyé à l'appareil avec la carte** : un script peut renvoyer une copie parfaite du modèle (100 points) ; seule parade, ne plus envoyer le modèle avant la réponse (incompatible avec l'affichage actuel). De même le verdict (« Raté / Presque / Réussi ») reste celui que l'utilisateur confirme : il ne peut que **réduire** ses points (un verdict « raté » = 0), pas les gonfler au-delà de la note réelle ; les semaines passées ne sont pas consultables (pas de « champion de la semaine » ni d'historique) ; le calcul parcourt les `review_logs` de la semaine pour tous les utilisateurs à chaque affichage (comme les séries).

## 6. Conventions

- Identifiants du code en **anglais** (les commentaires peuvent être en français) ; textes de l'interface, messages d'erreur et documentation en **français**.
- TypeScript strict côté web ; les types qui traversent la frontière API ↔ web vivent dans `libs/shared` (import `@kanadrill/shared`).
- API : validation par `class-validator` (`ValidationPipe` global, `whitelist` + `forbidNonWhitelisted`). Les routes protégées utilisent `@UseGuards(JwtAuthGuard)` et `@CurrentUserId()`.
- Migrations : **jamais** de `synchronize`. Après `npm run migration:generate -- apps/api/src/app/database/migrations/NomDeLaMigration`, **ajouter la classe générée à `MIGRATIONS`** dans `database/migrations/index.ts` (liste explicite : le bundle webpack n'a pas de glob de fichiers). Pareil pour toute nouvelle entité dans `database/entities.ts`.
- Front : composants standalone, signals, nouvelle syntaxe de template (`@if`, `@for`), Tailwind avec les couleurs de `styles.css` (`ink`, `paper`, `snow`, `line`, `seal`, et `on-ink` / `on-seal` / `on-ok` pour le texte sur fond plein : jamais `text-paper`) et la police `font-kana` pour le japonais. Le rouge `seal` est réservé aux actions importantes et aux erreurs. Mobile d'abord, focus visible, `prefers-reduced-motion` respecté.
- Aucun secret dans le dépôt : tout passe par `.env` (ignoré par git).

## 7. Pièges déjà rencontrés (ne pas les redécouvrir)

- **Versions ESM-only** : `@nestjs/config` 12, `@nestjs/typeorm` 12, `@nestjs/jwt` 12 et `@nestjs/passport` 12 ciblent Nest 12 et cassent Jest/webpack en CJS. Rester sur `@nestjs/config` ^4, `@nestjs/typeorm` ^11, `@nestjs/jwt` ^11, `@nestjs/passport` ^11 tant que Nest reste en 11.
- **`.npmrc` avec `legacy-peer-deps=true`** : sans lui, `npm install` échoue sur les dépendances croisées d'Angular 22 / Nx.
- **Driver `pg`** : TypeORM le charge dynamiquement, Nx ne le détecte pas. L'`import 'pg'` dans `app.module.ts` est volontaire (sinon le conteneur de prod plante au démarrage).
- **Image API** : on n'utilise pas le `package-lock.json` généré par Nx (désynchronisé de son `package.json`, `npm ci` échoue) ; le Dockerfile fait un `npm install` sur le `package.json` épinglé.
- **Passport sans session** : `passport-oauth2` ne gère le `state` qu'avec une session serveur. Le `state` est donc géré par `OAuthGuard` (cookie signé). Sans `code` dans le callback (utilisateur qui refuse chez Discord), la lib relancerait le flux en boucle : le guard l'intercepte.
- **CLI TypeORM** : `migration:generate` ne résout pas `@kanadrill/shared` à l'exécution. Les entités n'importent que des **types** depuis `libs/shared` (pas de constante) ; sinon « Cannot find module '@kanadrill/shared' ».
- **PWA / service worker** :
  - **`/api` doit rester hors du service worker.** Par défaut il répond `index.html` à toute navigation ; or la connexion Discord et son retour sont des navigations vers `/api/auth/discord…`. C'est le rôle de `"!/api/**"` dans `navigationUrls` (`ngsw-config.json`) ; `dataGroups` doit rester vide. Un test (`pwa.spec.ts`) le garde.
  - **nginx ne doit jamais mettre en cache** `ngsw-worker.js`, `ngsw.json`, `safety-worker.js`, `manifest.webmanifest`, sinon les mises à jour n'arrivent plus. Leur règle doit venir **avant** la règle de cache d'un an sur les `.js`, et n'utiliser que `expires -1` : un `add_header` dans un `location` fait perdre au bloc les `add_header` du bloc `server` (CSP, nosniff).
  - Le service worker n'existe que dans le **build de production** (`nx build web`) ; `nx serve` n'en a pas. Pour le tester en local : construire l'image web (`docker build -f apps/web/Dockerfile .`) ou `docker compose up --build` ; `localhost` compte comme contexte sécurisé, HTTPS n'est requis qu'ailleurs.
  - Un navigateur garde l'ancienne version tant que l'utilisateur n'a pas rechargé : d'où la bannière de mise à jour. **Secours** si un service worker défectueux est déployé : `safety-worker.js` (livré avec Angular) désinstalle le service worker ; il suffit de le servir sous le nom `ngsw-worker.js`.
  - L'icône est un « か » **avec le point rouge en bas à droite** : en haut à droite, il se lit comme un dakuten (« が »).
- **Kanji : données et déploiement** : `apps/api/src/assets/kanji.json.gz` est lu au démarrage par le seed ; webpack le copie dans `dist/apps/api/assets` et le **Dockerfile de l'API doit copier ce dossier** à côté de `main.js` (sinon l'API plante au démarrage : « Données des kanji introuvables »). Pour régénérer : `python3 tools/generate-kanji-data.py` (télécharge KANJIDIC2, KanjiVG et la liste JLPT ; le nombre de kanji peut varier légèrement, les tests donnent des bornes).
- **TypeORM `query()` et `DELETE`** : pour un `DELETE … RETURNING` brut, `dataSource.query()` renvoie **`[lignes, nombre]`** (et non les lignes comme pour un `SELECT` ou un `INSERT`) : tester `rows.length` sur le résultat brut ne dit rien.
- **Requêtes SQL brutes à paramètres** : tous les `$n` déclarés doivent être référencés par la requête (« could not determine data type of parameter $1 » sinon) ; le décompte et la page de `KanjiService.list` construisent donc leurs filtres chacun avec leur numérotation.
- **Sessions et kanji** : la composition ne charge **jamais** les 10 000 kanji ni leurs tracés (10 Mo) : seuls les kanji du dictionnaire sont lus, sans `metadata` ; les tracés ne sont chargés que pour les cartes de tracé, et les leurres de QCM de sens viennent d'un tirage de 400 kanji. Garder cette discipline pour toute nouvelle requête sur `items`.
- **UUID** : générés par `pgcrypto` (`gen_random_uuid`, natif depuis Postgres 13), aucune extension à installer.
- **Formulaires Angular** : un `<form>` avec seulement `ReactiveFormsModule` se soumet nativement (rechargement de page) ; utiliser `(submit)` + `preventDefault()` ou importer `FormsModule`.
- **IP réelle** : nginx (conteneur web) ne fait confiance à `X-Forwarded-For` que depuis les réseaux privés ; l'API a `trust proxy = 1`. Si un CDN (ex. Cloudflare en mode proxy) est placé devant, adapter la config pour que la limitation de débit voie la vraie IP.
- **Tests d'intégration : ils tournent sur `TEST_DATABASE_URL`, jamais sur la base du `.env`.** `ConfigModule.forRoot()` lit `process.env` à l'**import** de `AppModule` ; définir `DATABASE_URL` dans un `beforeAll` est trop tard, et les specs se connectaient alors à la **base de dev** et y faisaient leur `TRUNCATE users CASCADE` (compte, progression et sessions de dev effacés à chaque exécution ; découvert au lot C). Correctifs : `apps/api/jest.setup-env.ts` (Jest `setupFiles`) fixe l'environnement avant tout import et **refuse** une `TEST_DATABASE_URL` dont le nom de base ne contient pas « test » ; `assertTestDatabase()` est appelé avant chaque `TRUNCATE`. Créer la base une fois : `docker compose -f docker-compose.dev.yml exec db createdb -U kanadrill kanadrill_test`. Les tests ouvrent leurs sessions avec `SessionService.issue(userId)` (un cookie signé à la main n'a plus de session en base : 401).
- **Tests d'intégration, suite** : ils partagent une même base (`TRUNCATE users`, migrations). Jest tourne avec `maxWorkers: 1` pour l'API (`jest.config.cts`) ; en parallèle, le test d'auth échouait au hasard. Si le flux de profil Discord change (`DiscordStrategy.userProfile`), adapter la simulation dans `auth.integration.spec.ts`.
